# 实施 Issue 24 LLM 提供商架构升级

## Goal

让用户既能从可信的内置提供商预设快速完成 AI 配置，也能继续创建完全自定义的提供商；应用按真实协议发送请求、按模型能力过滤可用项，并在模型发现失败时保持现有配置可用。

关联需求：[GitHub Issue #24](https://github.com/phoben/LingoStack/issues/24)。

## Background

- 当前配置把品牌、协议与模型 ID 压在同一个 `ProviderConfig` 中，仅有 `open_ai_compatible`、`anthropic`、`gemini`、`ollama` 四种类型，见 `crates/lingostack-core/src/config.rs:17-50`。
- 当前统一请求只含 `model`、`messages`、可选 `temperature`；Anthropic 的最大输出仍是适配器固定值，见 `crates/lingostack-llm/src/lib.rs:56-76` 与 `anthropic.rs:71-131`。
- 当前 Tauri 工厂按四种类型直接构建协议实现，OpenAI 兼容与 Ollama 共用 Chat Completions wire format，见 `src-tauri/src/commands.rs:1013-1042`。
- 当前设置页只支持手工输入名称、协议、Base URL、API Key 与逗号分隔模型，功能模型下拉不做能力过滤，见 `src/components/provider-form.tsx:9-63` 与 `src/components/settings-ai.tsx:119-139`。
- 既有调研确认应采用“随应用发布的静态预设目录 + 可编辑本地实例 + 协议适配 + 带来源的模型能力”，不引入代理、数据库或远程目录：`docs/research/issue-24-llm-provider-architecture.md`。
- 补充一手资料确认 DeepSeek 支持 ID 级模型发现；Ollama 原生 `/api/chat` 是逐行 JSON，本 Issue 仅继续使用其 OpenAI 兼容调用面，原生 `/api/tags` 只用于本地模型发现：`research/provider-ecosystem.md`。

## Requirements

### R1. 四层领域概念分离

配置与代码必须分离以下概念：

1. `ProviderPreset`：随应用发布的公开起点，包含品牌、协议、建议端点、认证方式、官方文档、可选发现配置和初始模型说明。
2. `ProviderInstance`：用户本机保存并实际用于请求的独立实例；可选记录 `preset_id`，但运行时不得依赖预设覆盖其已保存字段。
3. `Protocol`：至少区分 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 与 Gemini Generate Content；Ollama 首期使用 OpenAI Chat Completions 协议，不伪装成原生 Ollama chat。
4. `ModelDescriptor`：描述模型 ID、可用功能、上下文窗口、最大输出、参数支持及每项规格来源。

功能层继续只依赖 `LlmProvider::chat_stream`，不得按品牌分支调用。

### R2. 首批预设与自定义入口

设置页新增提供商时，“自定义”必须置首，并提供以下首批预设：

- OpenAI Chat Completions
- OpenAI Responses
- Anthropic Claude
- Gemini
- DeepSeek
- 智谱普通 API
- MiniMax
- 阿里百炼 / 通义
- Ollama（OpenAI 兼容调用）

选择预设后自动填充名称、协议、建议 Base URL/端点选项、认证要求和初始模型；生成的实例仍可编辑。更改到未经该预设验证的协议或端点时，实例仍可保存和调用，但不得继续显示已验证的在线发现能力，也不得继续使用该预设的已验证参数映射。OpenAI Responses 是首期例外：若改离官方端点，必须切换为其他可用协议或恢复官方端点后才能保存。

Kimi 与火山引擎不进入首批预设；用户可通过“自定义”接入。

### R3. 实例独立与配置版本

- 预设实例化时复制公开默认值；应用升级预设目录不得覆盖已保存实例、模型、用户规格覆盖或功能分配。
- `preset_id` 可选；自定义实例不得依赖任何预设。
- 本任务采用新的配置 schema，并明确版本；根据 Issue 当前范围，不实现旧 `ProviderConfig` 的自动迁移或向后兼容。旧开发配置应得到可操作的“不兼容/需重新配置”提示，而不是静默错配。
- API Key 仍只保存在本机配置文件中；所有 `Debug`、错误、fixture、前端错误文本和测试快照必须脱敏。

### R4. 独立的 OpenAI Responses 协议

- OpenAI Responses 使用独立请求体、端点与具名 SSE 事件解析，不得复用 Chat Completions 的请求结构或 delta 解析。
- 首期只有 OpenAI 官方预设可选择 Responses。
- DeepSeek、百炼、火山等兼容实现只有在各自请求和流式合约单独验证后才能开放，不因宣称兼容而自动启用。

### R5. 可选、显式触发的模型发现

- 只有预设、协议与端点仍匹配已验证发现配置时显示“刷新模型”。
- 首期发现覆盖 OpenAI、Anthropic（含分页）、Gemini、DeepSeek、MiniMax 与 Ollama 本地 `/api/tags`；智谱与百炼首期保留手工模型，直到其当前账号/地域契约被单独固定。
- 在线发现只由用户显式触发，不在启动、打开设置或后台自动请求。
- 发现返回规范化候选，不直接保存配置；候选进入可输入的多选下拉框，用户选择后立即进入当前表单草稿，并可继续补充手工模型。
- 已加入草稿或已保存的模型再次出现在发现结果中时必须显示为已选；保存并重新编辑、再次刷新后仍保持已选，不得依赖额外的“添加所选模型”动作。
- 权限不足、分页失败、格式异常、返回为空或网络失败时，保留已有模型与未保存表单内容，不阻止手工输入、保存或后续调用。
- OpenAI、Anthropic、DeepSeek 等 ID 级列表不得被当作模型能力证明；Gemini 等响应中存在的限制也必须保留“提供商返回”来源。

### R6. 带来源的模型能力与覆盖

- 上下文窗口和最大输出值分别携带来源状态：随应用审核、提供商返回或用户覆盖。
- 随应用审核的数据保留官方来源 URL 与核验日期；用户覆盖必须在 UI 标记“未经应用核验”。
- 手工模型默认可用于现有文本功能，但其能力状态为未核验；用户可调整功能适用范围。
- 远程刷新按模型 ID 非破坏性合并：不得删除已有模型，不得覆盖用户值，也不得用 ID 级列表清空已审核能力。

### R7. 功能模型过滤与后端不变量

- 翻译、命名、词条解释、文档翻译继续复用现有功能分配，不新增品牌专属页面。
- 每个功能的候选模型按 `ModelDescriptor` 的功能能力过滤。
- 后端在发起请求前再次校验：提供商存在、模型存在、模型支持目标功能、生成参数与模型/协议匹配；隐藏选项不能替代后端校验。
- 删除提供商继续清理全部引用该实例的功能分配。

### R8. 生成参数

- 每个功能模型分配可保存独立的可选生成设置，至少包括温度和最大输出 Token。
- 参数只在模型能力与协议映射都明确支持时展示并发送；未设置时使用协议/提供商默认。
- OpenAI Chat 兼容提供商的最大输出字段差异必须由审核过的参数映射描述，不能假设所有兼容服务接受同一字段。
- 已审核参数映射必须与实例化时复制的协议和端点范围绑定；用户修改到范围外时自动退回“不发送可选参数”的保守行为，不能沿用旧映射。
- 思考控制只对明确支持的模型显示，并使用协议专用形状；不得提供对全部模型通用的“高级参数”字典。

### R9. 设置页体验与可访问性

- 沿用当前设置页的单层主面板、分割线行表与内联编辑方式，不新增嵌套卡片。
- 预设选择、发现加载、发现结果、失败和保存状态应有清晰可观察结果；异步区域使用稳定的 `aria-live` / `aria-busy`，持续失败使用 `role="alert"`。
- 模型输入框与“刷新模型”按钮共用一行；刷新成功后，远端模型候选直接进入该输入框的下拉列表，不再在字段下方渲染复选框列表与“添加所选模型”按钮。
- 模型控件必须同时支持键盘输入自定义模型 ID 与从发现结果中选择模型，并保留刷新失败时的既有输入。
- API Key 默认掩码；只有用户主动操作时临时显示。
- 中英文文案、键盘可达、焦点状态及空态必须与现有设置页一致。

### R10. 测试与文档同步

- Rust/TypeScript 配置镜像、共享 IPC fixture 与 Tauri 命令保持一致。
- 协议与模型发现测试全部使用 mock HTTP 服务，不使用真实 API Key 或互联网。
- 更新 `docs/lingostack-design.md` 的提供商、配置模型与测试说明；不新增目录，因此无需改变仓库布局图。
- 实施后按 IPC、配置与关键桌面流程的影响范围执行 Rust、前端、生产隔离和真实 Tauri E2E 门禁，并分别报告证据等级。

## Acceptance Criteria

- [ ] AC1：新增提供商时“自定义”位于首位，全部首批预设可见；选择任一预设会填入已审核的名称、协议、端点和认证要求。
- [ ] AC2：预设生成的实例可编辑并独立保存；升级/重新读取预设不会覆盖实例，自定义实例无需 `preset_id` 即可运行。
- [ ] AC3：旧 schema 不会被静默解释为新 schema；用户得到明确的重新配置提示。
- [ ] AC4：OpenAI Chat 与 OpenAI Responses 使用不同请求/流式解析实现，且只有 OpenAI 官方预设开放 Responses。
- [ ] AC5：现有 OpenAI Chat、Anthropic、Gemini 与 Ollama OpenAI 兼容调用继续通过协议合约测试。
- [ ] AC6：符合 R5 白名单的预设显示“刷新模型”；其他预设和失配端点不显示或禁用该动作并解释原因。
- [ ] AC7：发现结果可多选并与手工模型共存；选择即进入当前表单草稿，保存后重新编辑或再次刷新仍显示为已选；发现失败、空结果和分页失败不清空任何已有选择，也不阻止保存。
- [ ] AC8：上下文窗口与最大输出分别显示来源；用户覆盖后显示“未经应用核验”，且后续刷新不覆盖该值。
- [ ] AC9：温度、最大输出和思考控制只在模型与协议明确支持时显示；请求 fixture 证明只发送正确映射的字段。
- [ ] AC10：翻译、命名、词条解释和文档翻译的模型下拉按能力过滤；构造非法配置绕过 UI 时后端拒绝请求。
- [ ] AC11：API Key、认证头和完整敏感响应不出现在 `Debug`、错误文本、测试快照或 UI 告警中。
- [ ] AC12：自动化覆盖预设实例化、自定义实例、新 schema、Responses 请求与事件、现有协议回归、发现正常/分页/失败、非破坏性合并、能力过滤、参数显示和保存失败。
- [ ] AC13：Windows 本机真实 Tauri E2E 覆盖预设保存、模型分配与至少一个 Responses fixture 流；真实第三方账号、供应商额度和 Linux/macOS 运行不由该结果替代。
- [ ] AC14：模型输入框与刷新按钮同排；刷新后可通过同一多选控件展开候选、键盘选择候选或输入自定义模型 ID，字段下方不再出现独立复选框结果区和“添加所选模型”按钮，刷新失败不清空草稿。

## Out of Scope

- 旧配置自动迁移、双写或向后兼容。
- Kimi 与火山引擎首批预设。
- DeepSeek、百炼、火山等第三方 Responses 兼容开放。
- Ollama 原生 `/api/chat` 调用适配；首期仅通过 OpenAI 兼容接口调用。
- 远程预设目录、签名更新、后台刷新或供应链机制。
- 本地代理、协议转换网关、故障转移、请求路由、SQLite 提供商数据库、云同步或跨 AI 工具配置同步。
- 内置额度、订阅、账号体系、遥测、真实第三方 API CI。
- 图片 OCR、视觉翻译与 Issue #25 的能力。

## Key Decisions

- 采用一个跨层 Trellis 任务完成本 Issue，不拆分子任务：配置、协议、IPC 和设置页共享同一 schema 与验收链，分开启动会造成中间状态不可运行；`implement.md` 通过阶段门禁控制顺序。
- 预设是实例化模板，不是运行时品牌开关；保存后的实例是事实来源。
- 模型发现是设置流程的可选读取能力，不扩展 `LlmProvider` 的聊天 interface；功能调用仍只依赖 `chat_stream`。
- 一个提供商继续支持多个模型；模型输入文字与下拉勾选共同编辑同一份表单模型集合，不再维护需要二次确认才能合并的临时发现选择。
- 以 Issue 当前 triage 简报为范围事实：不做旧配置迁移，Responses 首期只开放 OpenAI，catalog 随应用发版。
- 当前没有阻塞性的产品决策或开放问题；实施开始仍需用户在最终计划后再次确认。
